What actually gets hashed: bytes

Hash functions never see letters, only bytes. Plain English letters take one byte each in UTF-8. Try an accented letter or an emoji: it takes two to four bytes (highlighted).

Hex, Base64 and binary are the same hash. They’re just different ways to write the same bits. Hex uses 4 bits per character, Base64 uses 6, binary uses 1. Switch formats above and the fingerprint stripes stay identical.

Why there’s no HMAC for CRC32. CRC32 is linear: an attacker can change a message and calculate exactly how to fix the checksum, key or no key. HMAC needs a cryptographic hash underneath, so the CRC32 row turns itself off when you enable a key.

MD5, SHA-1 and SHA-256 are Merkle–Damgård designs: the input is padded and processed in 64-byte blocks, and the output is the final internal state. SHA-512 uses 128-byte blocks. SHA3-256 is a sponge (Keccak) and releases only part of its 1600-bit state. That difference is why plain SHA-256 is vulnerable to length-extension attacks and SHA-3 is not. See the HMAC lab.

Collisions and the birthday paradox

A collision is two different inputs with the same hash. They must exist, because there are infinitely many inputs and only so many outputs. The question is how hard they are to find. To make it possible here, we chop SHA-256 down to just a few hex digits.

4,096
possible fingerprints expect a collision after about 80 tries

That’s the birthday paradox: with N possible values you expect a repeat after roughly √(πN/2) tries, not N. In a room of 23 people, two probably share a birthday.

Collision resistance is half the bit length: a 256-bit hash gives about 2¹²⁸ security against collisions. SHA-1’s 160 bits should mean 2⁸⁰ work, but the 2017 SHAttered attack needed only about 2⁶³, and later chosen-prefix attacks made it cheaper still. MD5 collisions now take seconds on a laptop.

Proof of work

Since you can’t steer a hash, the only way to get one that starts with zeros is to keep guessing. Blockchains use this as a costly puzzle: change the nonce, hash, repeat, until the hash starts with enough zeros.

Nonce 0

Each extra zero makes the puzzle 16 times harder. Yet anyone can check a solution with a single hash. Hard to find, instant to verify: that asymmetry is the whole idea.

Catch the tampered download

The publisher of an installer script lists its SHA-256 on their official site. You found it on three mirrors. They look the same, but only one is genuine. Hash each and decide which to trust.

Published SHA-256 (from the official site)

The published hash only helps if you get it from a source the attacker can’t also change, ideally a different channel. A hash on the same compromised mirror proves nothing. That’s why serious projects also sign their hashes.

The lesson. A plain hash detects accidents, but anyone can compute SHA-256, so Mallory just recomputes it. HMAC mixes in a secret key that only Alice and Bob know, so Mallory can’t produce a valid tag for her new message.

Why not just tag = SHA-256(key ‖ message)? Because SHA-256 outputs its full internal state, an attacker who sees a tag can keep hashing from it and append data, producing a valid tag for message ‖ padding ‖ extra without the key. This is a length-extension attack. HMAC’s nested construction, H((K⊕opad) ‖ H((K⊕ipad) ‖ m)), blocks it. SHA-3 is immune by design.

How not to store passwords

A website was breached and its user table leaked. The passwords were hashed, so they’re safe… right? Attackers keep giant tables of precomputed hashes for common passwords. Run the lookup.

Make each guess expensive

Salt stops precomputed tables, but MD5 and SHA-256 are still far too fast; a GPU tries billions per second. Password hashing functions repeat the work on purpose. Slide the cost and feel it.

OWASP currently suggests at least 600,000 iterations for PBKDF2-HMAC-SHA256. The attacker estimate assumes a GPU rig doing 10 billion SHA-256 operations per second; it’s a rough illustration, not a benchmark.

PBKDF2 is slow but cheap in memory, so GPUs and ASICs still parallelize it well. bcrypt adds some memory pressure; scrypt and Argon2id are memory-hard, forcing each guess to use many megabytes, which kills the GPU advantage. Argon2id is the current default recommendation for new systems.
