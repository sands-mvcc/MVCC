Guided labs

      Why firewalls exist

      A network firewall enforces a security policy at the boundary between networks of different trust. It decides, packet by packet or session by session, what may cross.

      Organizations divide their networks into zones that group systems with similar trust and exposure. A typical edge design has an untrusted Internet zone, a screened subnet (DMZ) for public-facing servers, an internal user zone, and a restricted data or server zone. The firewall sits between them and is the only path from one zone to another.

      Analogy. Think of a secure building’s lobby desk. Visitors (packets) state who they are and where they’re going; the guard checks a list (the rule base) from top to bottom and acts on the first entry that applies. Anyone not on the list is turned away.

      Default deny

      Well-designed policies deny by default and allow only what the business needs. Every vendor ends its rule base with an implicit deny for traffic between zones. The analyst’s job is to write the smallest set of allow rules that supports the business, a practice called least privilege.

      What a firewall cannot do

      • It can’t inspect traffic that never crosses it, such as two hosts on the same switch in the same zone.
      • It can’t see inside encrypted traffic unless it performs TLS decryption.
      • It doesn’t replace endpoint protection, patching, or identity controls; it is one layer of defense in depth.

      Form factors and deployment

      The same policy concepts appear in hardware, software and cloud services. Analysts are expected to recognize all of them.

      Form factors

      • Network appliances at the perimeter or data center core, often in a high-availability pair (active/passive or active/active) that shares session state so failover doesn’t drop connections.
      • Virtual firewalls running on hypervisors to segment virtual machines, sometimes enforcing policy at each VM’s network interface (microsegmentation).
      • Host-based firewalls such as Windows Defender Firewall, nftables/iptables, ufw, or firewalld, which protect a single endpoint.
      • Cloud-native controls: AWS security groups (stateful) and network ACLs (stateless), Azure network security groups, and managed cloud firewalls.
      • Firewall as a service delivered from the cloud as part of a secure access service edge (SASE) design for remote users and branches.

      Deployment modes

      • Routed (Layer 3): each interface has an IP address and the firewall is the default gateway for its zones. This lab uses routed mode.
      • Transparent (Layer 2 or virtual wire): the firewall bridges traffic without readdressing, useful when inserting a firewall into an existing network.
      • Tap or mirror mode: the firewall sees a copy of traffic for visibility only and can’t block.

      Common architectures

      A three-legged firewall connects Internet, DMZ and internal zones to one device. A back-to-back (dual-firewall) DMZ places the DMZ between an outer and inner firewall, often from different vendors. Internal segmentation firewalls separate user, server and operational technology networks to limit lateral movement.

      First match wins

      The policy lookup stops at the first rule whose source zone, source address, destination zone, destination address, service and (on an NGFW) application all match. Rule order matters: a broad rule placed above a narrow one shadows it, so the narrow rule never takes effect. Place specific rules above general ones, and deny rules for exceptions above the allows they carve from.

      Deny, drop or reject?

      Drop (shown as Deny in this lab) silently discards the packet; the sender waits and times out, which gives attackers less information. Reject discards it and returns a TCP reset or ICMP unreachable message, which fails fast for internal users but confirms the firewall’s presence to scanners.

      Stateless versus stateful

      The single most important leap in firewall history was remembering conversations.

      When a user browses a website, the request leaves from a random ephemeral port (49152–65535) to port 443. The reply comes back from port 443 to that ephemeral port. A stateless packet filter has no memory, so to let replies in, an administrator must allow inbound traffic to high ports, which also lets an attacker reach any service listening on a high port, including RDP on 3389.

      A stateful firewall records each allowed connection in a session table: source and destination address, ports, protocol, and TCP state. Replies that match an existing session are forwarded without a rule lookup. Unsolicited packets that claim to be replies, such as a TCP ACK with no matching session, are dropped. Sessions expire after an idle timeout, so the table doesn’t grow forever.

      Try it. In the lab, set the firewall type to Packet filter and send User PC browses a website, then send the reply. Switch to Stateful and repeat. Lab 3 grades you on this.

      Address translation and VPNs

      Firewalls usually perform network address translation and terminate encrypted tunnels, so analysts must read both in logs.

      Network address translation

      • Source NAT / PAT lets many private hosts share one public address. In this lab, outbound traffic is translated to 192.0.2.1.
      • Destination NAT (static NAT or port forwarding) publishes an internal server. Here, 192.0.2.10 maps to the web server at 172.16.10.10.
      • Vendors differ on whether policy matches the pre-NAT or post-NAT address. Cisco ASA (8.3 and later) and this lab match the real (post-NAT) server address; Palo Alto Networks matches the pre-NAT destination IP but the post-NAT zone. Always check the platform documentation.

      VPNs

      Firewalls commonly terminate site-to-site IPsec tunnels between offices and remote-access VPNs (IPsec or TLS) for users. Decrypted VPN traffic should land in its own zone so it is subject to the same policy as any other traffic, rather than being treated as fully trusted.

      Next-generation security services

      An NGFW shifts policy from “which port” to “which application, which user, and is it malicious”.

      • Application identification classifies traffic by its signatures and behavior, so BitTorrent or Tor tunneled over port 443 is recognized and can be blocked while normal HTTPS is allowed. Identification often takes several packets, so the session is initially allowed and then re-evaluated.
      • User identification maps IP addresses to directory users and groups, enabling rules such as “Finance group may reach the ERP server”.
      • Intrusion prevention (IPS) matches exploit and vulnerability signatures inside allowed sessions and drops malicious packets.
      • TLS/SSL decryption lets the firewall inspect encrypted traffic. It requires a trusted certificate on endpoints and a policy that exempts sensitive categories such as health and banking.
      • URL filtering, DNS security, sandboxing and threat-intelligence feeds block known-bad destinations and detonate unknown files.
      Key idea. Allowing a service is not the same as trusting it. Attach threat-prevention profiles to every allow rule that faces untrusted networks. Lab 6 tests this.

      Managing firewalls over time

      Most firewall breaches trace back to configuration drift, not product flaws.

      Daily and weekly operations

      • Review logs and alerts, and forward them to the SIEM with accurate time (NTP).
      • Investigate unexpected denies and spikes; correlate with IDS, endpoint and authentication data.
      • Process change requests: verify business justification, test, schedule a window, document, and have a rollback plan.

      Periodic hygiene

      • Rule base reviews to remove shadowed, redundant, unused, expired and overly permissive rules. Hit counters and audit tools support this; try Audit rule base in the lab.
      • Hardening: restrict management access to a dedicated network, use MFA and role-based admin accounts, disable unused services, and change default credentials.
      • Backups and version control of configurations, and tested restore procedures.
      • Firmware and signature updates on a schedule, with emergency patching for exploited vulnerabilities.
      • Compliance evidence for frameworks such as PCI DSS Requirement 1, NIST SP 800-41, and CIS Controls.
