What Is a STIG?

The big picture before we get hands-on.

A Security Technical Implementation Guide (STIG) is a configuration standard published by the Defense Information Systems Agency (DISA) that tells you exactly how to securely configure a specific product — an operating system, network device, database, browser, or application.

Each STIG is a collection of rules. Every rule says what must be configured, why it matters, how to check it, and how to fix it. STIGs are required on U.S. Department of Defense (DoD) systems and are widely adopted by federal agencies, defense contractors, state governments, utilities, and any organization that wants a hardened, auditable baseline.

Key idea: Out of the box, most products ship configured for convenience. A STIG reconfigures them for security — and gives you a way to prove it.

🎯 Learning Objectives

By the end of this lesson you will be able to:

  • Explain the purpose of STIGs, SRGs, and SCAP and how they fit into the Risk Management Framework (RMF).
  • Interpret every field of a STIG rule and classify findings as CAT I, II, or III.
  • Describe the STIG compliance lifecycle and the tools used at each step.
  • Perform check-and-fix procedures on Windows 11, Cisco IOS XE, and RHEL 10.
  • Complete a STIG checklist with correct statuses and defensible comments.
  • Map STIG skills to cybersecurity job roles and certifications.

The STIG family tree

📜
NIST SP 800-53
The "what": security controls (e.g., CM-6 Configuration Settings)
📘
SRG
Security Requirements Guide — requirements for a class of technology (e.g., all operating systems)
🔧
STIG
The "how": product-specific settings (e.g., Windows 11, RHEL 10)
🤖
SCAP Benchmark
Machine-readable version of a STIG so tools can check it automatically
Version note: DISA updates STIGs on a regular release cycle. Rule IDs, severities, and values in this lesson are representative examples for learning. Always download the current STIG from the DISA STIG Library before assessing a production system.

Severity Categories: CAT I, II, III

Severity drives priority. CAT I findings are fixed first — and can block a system from going live.

✓ Complete
CAT I · HIGH

Any vulnerability whose exploitation will directly and immediately result in loss of Confidentiality, Integrity, or Availability.

CAT II · MEDIUM

Any vulnerability whose exploitation has a potential to result in loss of Confidentiality, Integrity, or Availability.

CAT III · LOW

Any vulnerability whose existence degrades measures that protect against loss of Confidentiality, Integrity, or Availability.

🏛️ Why Employers Care

  • DoD & federal systems must be STIG-compliant to receive and keep an Authorization to Operate (ATO).
  • Defense contractors use STIGs as a proven hardening baseline when meeting NIST SP 800-171 configuration requirements and preparing for CMMC assessments.

  • Private sector organizations (utilities, healthcare, finance) use STIGs or the similar CIS Benchmarks to meet auditors and insurers.

🪟 Windows 11 STIG

Endpoint hardening for the most common workstation in government and industry.

✓ Complete

What it covers

The Microsoft Windows 11 STIG contains hundreds of rules spanning account policies, audit policy, user rights, security options, Windows Defender, BitLocker, PowerShell logging, and administrative templates. Rule IDs begin with WN11- followed by a category code:

PrefixArea
WN11-00-General / system requirements (e.g., BitLocker, Secure Boot)
WN11-AC-Account policies (password, lockout)
WN11-AU-Audit policy
WN11-CC-Computer configuration (administrative templates)
WN11-SO-Security options
WN11-UR-User rights assignments

How pros apply it

  1. Never hand-edit one machine at a time in production. Import the DISA STIG GPO package into Group Policy (or build an Intune baseline for cloud-managed devices).
  2. Link the GPO to a test OU first, validate line-of-business apps, then roll to production OUs.
  3. Scan with SCAP Compliance Checker (SCC) or Evaluate-STIG to auto-check most rules.
  4. Manually review rules SCAP can't check (e.g., "only authorized software is installed").
  5. Export results to a checklist (.cklb) in STIG Viewer and document exceptions.
Pro tip: gpresult /h report.html and rsop.msc show which GPO actually set a value — essential when a STIG setting "won't stick."

🔀 Cisco IOS XE STIGs

Network devices get multiple STIGs — one for management, one for each role the device plays.

✓ Complete
NDM

Network Device Management

How the device itself is managed: AAA, SSH, login banners, session timeouts, logging, NTP, SNMPv3, password storage. Applies to every router and switch. IDs look like CISC-ND-…

RTR

Router

How the device forwards traffic as a router: disable proxy ARP, directed broadcast, and IP source routing; protect routing protocols with authentication; filter at the perimeter. IDs look like CISC-RT-…

L2S

Layer 2 Switch

How the device switches: no user traffic on VLAN 1, disable DTP, change the native VLAN, shut unused ports, enable BPDU Guard, DHCP snooping, and Dynamic ARP Inspection. IDs look like CISC-L2-…

Key concept: A Catalyst switch doing inter-VLAN routing is assessed against NDM + L2S + RTR. Picking the right set of STIGs for each device is itself a graded skill on the job.

🐧 Red Hat Enterprise Linux 10 STIG

Linux server hardening with open-source automation built right into the OS.

✓ Complete

What it covers

The RHEL STIG covers authentication (PAM, faillock, pwquality), SSH, SELinux, auditd, firewalld, cryptographic policy and FIPS mode, file permissions, partitioning, package management, and removal of insecure services. Rule IDs follow the pattern RHEL-10-######.

Red Hat's built-in advantage

Red Hat ships the SCAP Security Guide (SSG) with a stig profile. Using OpenSCAP you can scan, generate an HTML report, and even generate Bash or Ansible remediation — all from the command line.

# install the tools
dnf install -y openscap-scanner scap-security-guide

# scan against the STIG profile
oscap xccdf eval --profile stig \
  --results results.xml --report report.html \
  /usr/share/xml/scap/ssg/content/ssg-rhel10-ds.xml

# generate an Ansible playbook to fix findings
oscap xccdf generate fix --fix-type ansible \
  --profile stig --output stig-fix.yml \
  /usr/share/xml/scap/ssg/content/ssg-rhel10-ds.xml

RHEL 10 change: FIPS mode is now enabled at installation (for example, the fips=1 boot option). The old fips-mode-setup tool is gone — so a server built without FIPS must be rebuilt. Plan hardening before you install!

👩‍🏫 Instructor Notes & Lab Extensions
  • Windows extension: In a Windows 11 VM, run SCC or Evaluate-STIG, import the DISA GPO package with LGPO or the Group Policy Management Console, then re-scan and compare scores.
  • Linux extension: On RHEL 10 (or a compatible rebuild such as Rocky/Alma 10), run the oscap scan, open report.html, then apply the generated Ansible playbook in a snapshot-protected VM.
  • Cisco extension: In Cisco Modeling Labs or Packet Tracer, give students a misconfigured topology and grade them on a before/after show run diff.
  • Break-it lesson: Apply a full STIG baseline to a test VM and have students troubleshoot what stopped working — this teaches why testing before production matters.
  • Writing assignment: Students write one POA&M entry and one risk-acceptance justification for an Open CAT II finding.
  • Assessment alignment: Objectives map to Security+ (hardening, secure baselines), Linux+ (security), CCNA (device security), and NICE work roles for systems administration and security control assessment.
